# KProxyable: Generated Code Architecture

This document serves as a technical reference for the code generated by the KProxyable KSP
processor. It explains the patterns, naming conventions, and discovery mechanisms that enable
high-performance, cross-platform proxies.

---

## 1. Proxy Implementation Classes

For every interface annotated with `@KProxyable`, the processor generates a concrete implementation
named `_InterfaceNameProxy`.

### High-Performance Lazy Descriptors

To minimize class-loading time and memory usage, descriptors (metadata) are initialized only when
the corresponding member is accessed for the first time.

**Pattern:**

- Backing Field: A `private var` in the companion object, prefixed with `_`.
- Check and Init: Inside the method/property, a null-check initializes the descriptor if needed.

```kotlin
public class _MyServiceProxy(private val handler: ProxyHandler) : MyService {
    override fun greet(name: String): String {
        // High-performance lazy initialization
        val descriptor = _greetDescriptor ?: FunctionDescriptor(
            name = "greet",
            returnType = TypeDescriptor(classifier = String::class, isNullable = false),
            parameters = listOf(ParameterDescriptor(name = "name", ...))
        ).also { _greetDescriptor = it }
        
        return handler.onCall(descriptor, listOf(name)) as String
    }

    public companion object {
        private var _greetDescriptor: FunctionDescriptor? = null
    }
}
```

### Standard Method Interception

Proxies override the following standard `Any` methods to delegate them to the `ProxyHandler`:

- `toString()`: Delegates to `handler.onToString()`.
- `equals(other: Any?)`: Delegates to `handler.onEquals(other)`.
- `hashCode()`: Delegates to `handler.onHashCode()`.

## 2. Registry Hierarchy

KProxyable uses a layered registry system to allow proxies from different modules to be discovered
at runtime.

### Layer 1: Module Registries

Generated in every module that contains `@KProxyable` interfaces.

- **Naming**: `com.elianfabian.kproxyable.generated.KProxyRegistry_<moduleName>`.
- **Role**: Contains a `when` block to create proxies for all interfaces defined *within that
  specific module*.

### Layer 2: Master Registries (Applications)

Generated only in application modules (detected by the Gradle plugin).

- **Naming**: `KProxyJvmImpl` (JVM) or `KProxyJsImpl` (JS).
- **Role**: Collects all module registries (from the app and its dependencies) into a single
  delegation chain.

**JVM Example:**

```kotlin
public object KProxyJvmImpl : KProxyFactory {
  override fun <T : Any> findProxy(handler: ProxyHandler, classifier: KClass<T>): T? =
      KProxyRegistry_app.findProxy(handler, classifier)
   ?: KProxyRegistry_library_a.findProxy(handler, classifier)
   ?: KProxyRegistry_library_b.findProxy(handler, classifier)
}
```

**JS Example:**

```kotlin
@JsExport
@JsName("KProxyJsImpl")
public object KProxyJsImpl : KProxyFactory {
  override fun <T : Any> findProxy(handler: ProxyHandler, classifier: KClass<T>): T? =
      KProxyRegistry_app.findProxy(handler, classifier)
   ?: KProxyRegistry_library_a.findProxy(handler, classifier)
}
```

### Layer 3: KMP Composite Actuals

When a KMP project defines an `expect object KProxy : KProxyFactory`, KSP generates the `actual`
implementation.

- **Role**: Delegates to the local module registry and all discovered dependency registries using
  the `?:` chain.

**Example:**

```kotlin
public actual object KProxy : KProxyFactory {
  override fun <T : Any> findProxy(handler: ProxyHandler, classifier: KClass<T>): T? =
      KProxyRegistry_my_kmp_app.findProxy(handler, classifier)
   ?: KProxyRegistry_common_lib.findProxy(handler, classifier)
}
```

## 3. The Discovery Engine

One of KProxyable's most powerful features is finding proxies across module boundaries without
manual registration.

### Breadcrumbs (Metadata)

When a module registry is generated, the processor also creates a "breadcrumb" file:

- **Path**: `META-INF/services/com.elianfabian.kproxyable.KProxyFactory`
- **Content**: The Fully Qualified Name (FQN) of that module's registry.

### Classpath Scanning

The KSP processor scans the full compile classpath for these breadcrumb files.

- **JAR Files (JVM)**: Scans the root `META-INF/services/`.
- **Klib Files (JS/KMP)**: Scans the internal path `default/resources/META-INF/services/`.

The registries found are combined into the Master Registry or the KMP Actual.

## 4. Platform Runtime Triggers

To start the discovery process in "Automagic" mode (zero boilerplate), the library needs to "find"
the generated code.

### JVM Target

Uses reflection to load the Master Registry:

```kotlin
val clazz = Class.forName("com.elianfabian.kproxyable.generated.KProxyJvmImpl")
val instance = clazz.getField("INSTANCE").get(null) as KProxyFactory
```

### JS Target

Uses a global discovery function generated by the processor to bypass the lack of reflection:

- **Generated Function**: `getKProxyJsImpl()` in the root package.
- **Runtime Lookup**: The `KProxyJs` object use a `js()` block to find and call this function in the
  module exports or `globalThis`.

## 5. Summary of Naming Conventions

| Component                 | Target Location                        | Naming Pattern                             |
|:--------------------------|:---------------------------------------|:-------------------------------------------|
| **Proxy Class**           | Interface Package                      | `_InterfaceNameProxy`                      |
| **Module Registry**       | `com.elianfabian.kproxyable.generated` | `KProxyRegistry_moduleName`                |
| **Master Registry (JVM)** | `com.elianfabian.kproxyable.generated` | `KProxyJvmImpl`                            |
| **Master Registry (JS)**  | `com.elianfabian.kproxyable.generated` | `KProxyJsImpl`                             |
| **JS Discovery Fun**      | Root Package                           | `getKProxyJsImpl()`                        |
| **Breadcrumb File**       | `META-INF/services/`                   | `com.elianfabian.kproxyable.KProxyFactory` |
